# Simulated Forest — Documentation

> **Disclaimer:** This document was generated by AI based on the specs and code I wrote manually, without AI assistance.

## Overview

A small terminal-based ecosystem simulation. Three kinds of entities (Grass, Rabbits, Wolves) live on a square grid, the Forest. The simulation advances in **ticks** (1 second per tick); on each tick every entity ages, optionally hunts, eats, reproduces, or dies. The loop ends when the grid is empty, printing how many ticks the forest survived.

|---|---|---|---|

| `max_hunger` | — | 100 | 150 |
| `hunger_threshold` | — | 70 | 50 |
| `hunger_attrition` | — | 5 | 5 |
| `reproduction_period` | 10 ticks | 8 ticks | 25 ticks |

Grass has no hunger system; it just loses 5 health per tick and dies after ~20 ticks unless it never gets a chance to reproduce first. Rabbits eat Grass; Wolves eat Rabbits.

## Mechanics

### Hunger & Health

Every tick, `hungry_or_starving()` runs on each entity:

- If `current_hunger > 0`: subtract `hunger_attrition` from hunger.
- If `current_hunger <= 0`: subtract `health_attrition` from health instead.
- If `current_health <= 0`: the entity dies and is removed from the simulation.

Eating fully restores both hunger and health to their max values.

### Seeking food

Once an entity's hunger drops below its `hunger_threshold`, it asks the Forest for a path to the nearest target (Grass for Rabbits, Rabbit for Wolves). The path is recomputed every tick — there is no caching on the Forest side, even though the specs called for it.

### Eating

`go_eat(consumer, path_and_target)` advances the consumer by one cell along the returned path. If the new position equals the target's position, the consumer's hunger and health are reset to max and the target's `current_health` is set to 0 (the target then dies during the starvation pass).

### Reproduction

`can_reproduce(count, parents, ticker, period)` returns `True` when **all** of:

- `instance_count >= parents_required` for that class,
- the global tick counter is divisible by the class's `reproduction_period`,
- the entity is not currently hungry,
- the total number of beings is below `dimensions ** 2`.

If those hold, the Forest is asked for a free cell and a new entity of the same class is spawned there. (Note: the specs described reproduction as "after eating Y prey", but the code went with a periodic, count-gated approach instead.)

## Forest Representation

The Forest is a square matrix of size `dimensions × dimensions`, with `1 <= dimensions <= 20`. Each cell holds **one** of:

- `None` — empty
- a reference to a `Grass`, `Rabbit`, or `Wolf` instance
- the string `'R'` — a temporary reservation marker used during pathfinding and spawning

Only one entity occupies a cell at a time. Unlike the specs (which proposed `[grass_id, rabbit_id, wolf_id]` per cell), there is no co-occupation.

Global counts are stored as **class attributes** on Grass, Rabbit and Wolf (`instance_count`), not on the Forest.

## Classes

### `Forest`

#### Attributes
- `_dimensions` — grid size
- `_matrix` — list of lists, the grid itself
- `_reserved = 'R'` — sentinel used to mark cells claimed mid-search

#### Methods

- `reset_forest()` — rebuilds `_matrix` as a `dimensions × dimensions` grid of `None`.
- `update_position(element, position)` — writes `element` into the cell at `position[0]`.
- `update_forest(instances)` — collects every entity's position, resets the matrix, and rewrites all entities back in. Called once per tick.
- `is_empty(position)` — boolean check on a single cell.
- `find_path(start_position=None, target_type=None)` — see below.
- `draw_matrix()` — returns a printable string with a random emoji variant per entity.
- `draw_debug_matrix()` — prints the raw matrix for debugging.

#### `find_path(start_position, target_type)`

A single method that does double duty depending on its arguments:

- **With `target_type`** (a class like `Grass` or `Rabbit`): runs a BFS from `start_position` over the 8 compass directions and returns `[path, target_instance]` for the nearest matching entity. As the BFS expands, it stamps each visited empty cell with `'R'` to avoid revisits. Returns `-1` if nothing is found.
- **Without `target_type`**: returns the coordinates of the nearest empty cell to `start_position` and reserves it with `'R'`. If `start_position` is also missing, it picks a random starting cell — this is how the initial population is placed and how new spawns get a slot.

### `LivingBeing` (base class)

Holds shared instance state: `_position`, `_path`, `_target`, `_current_health`, `_current_hunger`, plus property getters/setters.

Shared methods:
- `hungry_or_starving()` — the hunger-then-health attrition described above.
- `is_hungry()` — `current_hunger < hunger_threshold`.
- `can_reproduce(count, parents, ticker, period)` — described above.

### `Grass`, `Rabbit`, `Wolf`

Subclasses of `LivingBeing`, each with its own class-level constants. `Grass` overrides `hungry_or_starving()` (only loses health, never hunger) and `is_hungry()` (always `False`).

## Game Loop

Setup:

```
dimensions    = 6
max_beings    = dimensions ** 2  # 36
start_grass   = 5
start_rabbits = 2
start_wolf    = 2
```

The initial population is placed by calling `forest.find_path()` (no args) for each new entity, then `forest.update_forest(beings)` writes them in.

Each iteration of the main loop:

1. Increment `ticks`.
2. For every entity in `beings`:
   1. `hungry_or_starving()`.
   2. If it's a hungry Rabbit, ask the Forest for a path to a `Grass`. If it's a hungry Wolf, ask for a path to a `Rabbit`.
   3. If a path was returned, call `go_eat()` to move one step (and possibly eat).
   4. If not hungry and `can_reproduce(...)` is true, ask the Forest for a free cell and append a new same-class entity to a `new_beings` buffer.
   5. If `current_health <= 0`, decrement the class's `instance_count` and `pop` the entity from `beings`.
3. Extend `beings` with `new_beings`.
4. `forest.update_forest(beings)` rewrites the matrix from scratch.
5. Print the tick number, per-class counts, and the drawn matrix; `time.sleep(1.0)`.

Loop exits when `beings` is empty.

## Known Bugs (noted in source)

- **Diagonal bias in pathfinding.** With one target at `(3, 1)` and a searcher at `(0, 0)`, BFS returns `[(0,0), (1,1), (2,2), (3,1)]` instead of the shorter-feeling `[(0,0), (1,1), (2,1), (3,1)]`. The 8-direction expansion order favors diagonals.
- **Overlapping paths.** Two hungry entities can be handed paths whose next step is the same cell. While moving, one will overwrite the other in the matrix.
- **Mutating `beings` while enumerating it.** Dead entities are removed via `beings.pop(index)` inside `for index, entity in enumerate(beings)`, which can skip the entity now occupying that index on the following iteration.
